## HIGH (7)

### Admin session revocation is inert — deleting an `admin_sessions` row does not end the PHP session

- **Where:** `app/Middleware/AdminAuthMiddleware.php:37`  (lens: security)
- **Failure:** Admin A is signed in on two browsers (sessions S1 and S2). From S1 they POST /admin/account/password with a new password. The controller deletes every `admin_sessions` row for that admin except S1's and toasts "Password updated. Other sessions have been signed out." S2 then does GET /admin/users and is still fully authenticated: AdminAuthMiddleware::handle() reads only $_SESSION['admin_id'], re-loads the admin row (status still 'active'), and grants access. The same holds for the forgot-password reset at AuthController::resetPassword (line 527, `Database::delete('admin_sessions', ...)`), for AuthController::revokeSession (line 646), and for SecurityController::revokeSession → SecurityService::revokeSession (line 414) — the Security Centre reports "Session revoked." while the target keeps browsing, renewing the 7200 s idle window on every request. Concretely: an attacker holding a stolen `zuste_admin_session` cookie survives the victim's password reset indefinitely.
- **Evidence:** Read AdminAuthMiddleware::handle() (lines 22-49): it checks Session::get('admin_id'), loads the admin from `admins`, checks status/deleted_at, then calls touchSession(). touchSession() (lines 97-109) issues `UPDATE admin_sessions SET last_activity = NOW() WHERE id = :id AND admin_id = :admin_id` and discards the affected-row count — a deleted row is a silent 0-row update, not a rejection. `grep -rn admin_sessions app/` returns 19 hits and none of them is a read used as an authorization gate; the only SELECTs are AccessController:65 (a display counter), AuthController:547 (the account screen list), SecurityController:70/426 and SecurityService:401 (listing/lookup for the UI).
- **Fix:** In AdminAuthMiddleware::handle(), after loading the admin, require the session row to exist — e.g. make touchSession() return the affected-row count and, when it is 0, `Session::destroy()` and rejectUnauthenticated(). (Rows must then be created for every authenticated session, which grantSession() already does.)

### `roles.manage` can grant permissions the granting admin does not hold, enabling escalation to all 84 permissions

- **Where:** `app/Controllers/Admin/AccessController.php:378`  (lens: security)
- **Failure:** An admin at role level 70 holding `admins.manage` + `roles.manage` (both are is_available=1, delegatable permissions) does: (1) POST /admin/roles with name=X, level=69, permissions[]=1..84 — storeRole only checks `level < myLevel` and passes the id list straight to syncRolePermissions, so role X now holds `system.restore`, `users.impersonate`, `wallet.adjust`, `payments.refund`, `kyc.download`; (2) POST /admin/admins/{ownId} with role_id=X — updateAdmin calls assertCanManage(), which returns early because the target is the caller (line 493), then assertRoleAssignable(), which only compares levels (69 < 70) and passes. The caller now holds every permission in the system. Even without `admins.manage`, POST /admin/roles/{id} on any lower-level role (Support, level 30) grants all 84 permissions to every admin in it.
- **Evidence:** Read AccessController::storeRole (line 342) and updateRole (line 378): both call `PermissionService::syncRolePermissions($roleId, array_map('intval', $request->array('permissions')))` with no filter against the caller's effective set. Contrast updateAdminPermissions (lines 208-240), which does exactly that check and comments "nobody grants a permission they do not hold. Otherwise a delegated `roles.manage` becomes a route to every capability in the system by way of a second account." Read assertCanManage (line 489) — `if ((int) $target['id'] === $this->adminId($request)) { return; }` — and assertRoleAssignable (line 502), which compares only `level`. Confirmed against the live RBAC tables: 84 permissions exist, `roles.manage` is is_available=1, and the class docblock's invariant 1 covers role *level* only, never the permission set.
- **Fix:** In storeRole()/updateRole(), filter the submitted permission ids through the caller's own effective set (as updateAdminPermissions does via PermissionService::forAdmin + slugFor), refusing the request when any id maps to a slug the caller lacks. Additionally, refuse a self-targeted role change in updateAdmin() rather than returning early from assertCanManage().

- **Where:** `lib/core/utils/json.dart:60`  (lens: flutter)
- **Failure:** Json.map is `(value as Map?)?.cast<String,dynamic>() ?? const {}` — the cast THROWS on a JSON array, it does not default. PHP encodes an empty associative array as [] not {}, and two live endpoints do exactly that. (a) BookingController::present() line 490 runs `json_decode(..., true) ?: []`, so any deliverable whose metrics column is NULL/''/'{}' is serialised as "metrics":[]. Deliverable.fromJson (lib/models/booking.dart:393) calls Json.map(json['metrics']) and throws; the throw propagates through Json.list -> BookingDetail.fromJson -> bookingDetailProvider. Opening booking 421 or 429 renders the generic ErrorState ('We hit a snag') instead of the booking — on BookingDetailsScreen, DeliverableReviewScreen, PaymentScreen and CheckoutSuccessScreen, all four of which watch bookingDetailProvider. 29 of 69 rows in booking_deliverables are in that state today. (b) KycService::details() (app/Services/KycService.php:214) returns [] when the user has no kyc_brand_details/kyc_creator_details row, so GET /me/kyc sends "details":[]. KycOverview.fromJson (lib/models/kyc.dart:37) calls Json.map(json['details']) and throws, so KycStatusScreen and KycDetailsScreen error out for every user who has not yet saved a detail block — 3 of the 4 kyc_profiles in the database.
- **Evidence:** Ran a standalone probe through `dart run`: jsonDecode('{"metrics":[]}') then the same expression printed "THREW: type 'List<dynamic>' is not a subtype of type 'Map<dynamic, dynamic>?' in type cast". Queried the live DB via the app bootstrap: booking_deliverables total 69, 29 with NULL/''/'{}' metrics; replaying the controller's own line on those rows printed {"id":21,"booking_id":421,"metrics":[]}. Called KycService::details() for all four kyc_profiles: profile 2 returns an object, profiles 141, 116 and 115 return {"details":[]}. The widget tests pass only because test/support/mock_data.dart lines 834 and 843 model empty metrics as a Dart Map (<String, dynamic>{}), which the real backend never sends.

Optionally also fix the two backend emitters to cast to object, but the Dart helper is the one that promises never to throw.

### Admin database restore is broken: every DROP TABLE is skipped, so the first CREATE TABLE aborts the restore

- **Where:** `app/Services/BackupService.php:248`  (lens: deployment)
- **Failure:** Admin → System → Backups → Restore on any backup this platform has ever written. restore() splits the dump on `;` (splitStatements, line 274) and then skips any statement whose trimmed text starts with `--`. Because the splitter keeps the preceding comment lines in the same buffer, every `-- Table: X` + `DROP TABLE IF EXISTS \`X\`` pair becomes ONE statement beginning with `--` and is skipped. The `CREATE TABLE` that follows is executed against a table that was never dropped, so MySQL raises 1050 on the very first table (`activity_logs`), PDO (ERRMODE_EXCEPTION, Database.php:69) throws out of the loop, and the request 500s having restored nothing. The catch-all in App::renderException reports 'An unexpected error occurred.' There is no try/finally, so `SET FOREIGN_KEY_CHECKS=0` (line 243) is also left set. Net effect: the platform takes nightly backups (crontab `0 2 * * * backup:database`) that cannot be restored through the only UI that offers restore.
- **Evidence:** I ran a verbatim copy of splitStatements() + the line-248 skip filter over the real dump storage/backups/zuste-db-2026-08-04_161652.sql.gz (7,814,808 bytes, written by this same class's dumpWithPhp()). Result: 410 statements, 286 executed, 124 skipped — of the 125 `DROP TABLE` statements, 123 land in a skipped buffer while 124 `CREATE TABLE` statements are executed. Skipped example: "-- Table: activity_logs\nDROP TABLE IF EXISTS `activity_logs`". I then ran `CREATE TABLE \`activity_logs\` (...)` against the live database and got exactly: SQLSTATE[42S01]: Base table or view already exists: 1050 Table 'activity_logs' already exists. The same shape occurs with real mysqldump output, which also emits a `--` comment block immediately before each DROP TABLE. (deploy_helper.php's `restore` uses a single `$pdo->exec($whole_dump)` instead and does work — I verified multi-statement exec is enabled on this PDO connection — so only the admin path is broken.)
- **Fix:** In splitStatements(), strip `--` line comments and `/* */` blocks while scanning (install.php:584 already has a correct splitter that does this), or in restore() strip leading comment lines from each statement before the emptiness test instead of discarding the whole statement.

### api_logs grows without bound — one row per API request and no automated prune anywhere in cron

- **Where:** `app/Services/CronRunner.php:306`  (lens: performance)
- **Failure:** Every API request appends a row to `api_logs` (App.php:204 registers a shutdown function that calls ApiLogService::record). The only DELETE against that table is ApiLogService::prune() (ApiLogService.php:153), and its sole caller is the manual admin action DeveloperController::pruneApiLogs, wired to POST /admin/developer/api-logs/prune (routes/admin.php:289). CronRunner::rotateLogs() — the `logs:rotate` scheduled job — deletes only from `system_logs` (60 days) and `activity_logs` (365 days) and unlinks old files; `api_logs` is not touched. With the shipped defaults (developer.api_logging unset → true, security.api_log_sample_rate = '100' → keep everything) an unattended production install never deletes a request-log row. On this install 18,928 rows / 8.53 MB accumulated in the 27 hours between MIN(created_at)=2026-08-03 14:06 and MAX=2026-08-04 16:56, from test traffic alone. The table already has more index than data (INDEX_LENGTH 5,259,264 vs DATA_LENGTH 3,686,400), so per-request INSERT cost keeps rising as four secondary indexes grow, and every /admin/developer aggregate (ApiLogService::overview) scans an ever-larger table.
- **Evidence:** Read CronRunner.php:70-95 (the job match arm — 'logs:rotate' => self::rotateLogs()) and CronRunner.php:306-331 (rotateLogs body: system_logs + activity_logs only). Read ApiLogService.php:44-170. `grep -rn "ApiLogService::prune" app/ scripts/` returns exactly one hit, DeveloperController.php:300. Queried information_schema and api_logs directly for the row count, size and created_at range quoted above; read the two settings back through Config::setting.
- **Fix:** Add the request log to the same rotation job, e.g. in CronRunner::rotateLogs(): `$apiRows = ApiLogService::prune(Config::settingInt('developer', 'api_log_retention_days', 30));` and return it alongside system_logs/activity_logs, so retention is enforced without an operator clicking a button.

### GET /bookings/{id}/coupons is an N+1 whose inner query is a full table scan: validate() re-fetches each coupon with UPPER(`code`), defeating the unique index

- **Where:** `app/Services/CouponService.php:319`  (lens: performance)
- **Failure:** offersForBooking() iterates `self::available($userId)` and calls self::validate() for every coupon. available() (line 355) selects every active public coupon with no LIMIT and already runs one `SELECT COUNT(*) FROM coupon_redemptions` per coupon (line 373). validate() then re-fetches the same coupon with `SELECT * FROM coupons WHERE UPPER(code) = :code` (line 50) — EXPLAIN reports `type=ALL, key=(none)`, i.e. a full scan of `coupons` — plus another coupon_redemptions COUNT (line 95) and, for applies_to = first_booking/brands/creators, a third query in assertEligible. Measured live on booking 695 (brand 2078): 29 statements / 27.4 ms for 7 public coupons. The cost is linear in the number of public coupons, so a marketing setup with 200 public codes turns one checkout screen into ~800 statements, 200 of them full scans of `coupons`. The same UPPER() scan sits on the payment path too — PaymentService.php:48 (applyToBooking) and :75 (reverifyForCharge) both funnel into validate().
- **Evidence:** Read CouponService.php:37-121 (validate), 296-346 (offersForBooking) and 348-386 (available). Ran offersForBooking() in-process against the live DB with a Database::queryCount() delta → 29 queries / 27.4 ms / 7 offers, and confirmed `SELECT COUNT(*) FROM coupons WHERE is_active=1 AND is_public=1 AND deleted_at IS NULL` = 7. EXPLAIN of the two predicate forms: `UPPER(code) = 'WELCOME10'` → type=ALL, key empty, rows=15; `code = 'WELCOME10'` → const via uq_coupons_code. information_schema shows coupons.code is utf8mb4_unicode_ci (case-insensitive), and line 43 already does strtoupper($code) in PHP, so the UPPER() is doubly redundant.
- **Fix:** Drop UPPER() from line 50 so `uq_coupons_code` is used; replace the per-coupon redemption COUNT with one `SELECT coupon_id, COUNT(*) ... WHERE user_id = :u GROUP BY coupon_id` before the loop; and add a validate-from-row overload so offersForBooking passes the coupon row it already holds instead of re-querying it per iteration.

### Opening a chat rewrites read_count on every inbound message in the thread, not just the newly-read ones

- **Where:** `app/Services/MessageService.php:378`  (lens: performance)
- **Failure:** GET /conversations/{id}/messages calls MessageService::markRead (MessageController.php:97, "Opening the thread marks it read"). Inside the transaction, once any receipt was updated, markRead runs `UPDATE messages m SET m.read_count = (SELECT COUNT(*) FROM message_receipts r WHERE r.message_id = m.id AND r.read_at IS NOT NULL) WHERE m.conversation_id = :conversation_id AND m.sender_id <> :user_id`. There is no bound on which messages — it targets the whole conversation. EXPLAIN on the live DB gives `table=m type=range key=idx_messages_conv rows=25` (the entire conversation) with a `DEPENDENT SUBQUERY` on message_receipts per row. So a user who opens a 10,000-message thread to read one new message rewrites ~5,000 rows and executes ~5,000 correlated COUNTs, holding row locks across the whole thread inside a transaction, and re-writes values that were already correct. Cost is O(thread length) per thread open, growing forever for long-running brand↔creator conversations.
- **Evidence:** Read MessageService.php:348-388 and MessageController.php:60-104. Ran `EXPLAIN UPDATE ...` (read-only) against conversation 807 / user 1008 — the busiest conversation in the DB — yielding the range plan and DEPENDENT SUBQUERY above; `SELECT COUNT(*) FROM messages WHERE conversation_id=807 AND sender_id<>1008` = 12, i.e. all 12 inbound rows are rewritten regardless of how many were actually unread.
- **Fix:** Scope the UPDATE to the messages just marked, e.g. capture the participant's previous `last_read_message_id` before the receipts UPDATE and add `AND m.id > COALESCE(:previous_last_read_message_id, 0)`, or collect the message ids the receipts UPDATE touched and drive the read_count refresh from that id list.

PHP only applies the open_basedir check to session.save_path in OnUpdateSaveDir, and only when the ini is altered at PHP_INI_STAGE_RUNTIME or PHP_INI_STAGE_HTACCESS; the files save handler itself does not re-check open_basedir when opening the session file. FPM applies pool php_value/php_admin_value entries via zend_alter_ini_entry at PHP_INI_STAGE_ACTIVATE, which is neither of those stages. I proved this empirically on PHP 8.2.12: `php -d open_basedir=D:/zustee.com -d session.save_path=<dir outside it> -r 'session_start(); $_SESSION["a"]=1;'` returned true and wrote sess_ok8avqjq6ianp3h4lho2tne1sf into the out-of-basedir directory, while the same open_basedir did block file_get_contents('C:/Windows/win.ini') ('Operation not permitted') — so the restriction was active. By contrast `ini_set('session.save_path', <outside>)` at runtime did fail with the exact open_basedir message, confirming the check is gated on the runtime stage only. The admin panel is therefore not locked out.
